# Ion IDE architecture performance audit

## Baseline and decision

Keep Electron and Monaco for this release. The largest standing memory cost is the desktop runtime and its graphics, network, and renderer processes. The production 0.2.0 Welcome screen showed about 415 MiB summed resident memory after two minutes, before Monaco, an optional panel, or a compiler had started. With one C file open the measured process family used about 512 MiB RSS, and with the medium project expanded it used about 566 MiB. The compressed Apple Silicon installer was 120,714,752 bytes (115.12 MiB), including Electron. The measurements are from an Apple M3 with 24 GiB RAM on arm64 macOS 27.2. [Production measurements and raw-data paths](PERFORMANCE.md)

Summed RSS can count shared mappings more than once. The audit uses both summed RSS and macOS's per-process attributed physical footprint, and keeps their results separate. A 300 MB target is 286.1 MiB if interpreted as decimal MB. An apparent threshold crossing caused by switching counters is a measurement difference. The 0.2.0 summed-RSS baseline exceeds the provisional 300 MB Welcome and 400 MB small-file targets and fits below 600 MB for the measured project. The newer 75-second production baseline reported 113.48 MiB attributed on Welcome, 244.51 MiB with one C file, and 267.27 MiB with the medium project. All three fit those budgets when assessed as attributed footprint. In a separate 0.2.0 close test, three Electron processes remained after closing the final window, with 321.89 MiB RSS and 93.72 MiB attributed. Quitting and last-window closure therefore need separate checks. The short tab-cycle runs help locate retention, but do not establish long-term leak freedom.

## Repository map

| Area | 0.2.0 resource behavior and exposure |
| --- | --- |
| Startup and core | `scripts/build.mjs` produces a small Electron main entry, preload and local Vite assets. `src/main/index.ts` takes a single-instance lock, installs scoped IPC and the local application protocol, and opens one BrowserWindow. The React Welcome uses preferences and recents. Neither an editor model nor a language worker is needed to display it. |
| Process isolation | Electron main owns files, native dialogs, execution and credentials. Its Chromium renderer displays React and Monaco. The GPU helper services compositing, and the utility helper supplies Chromium's network service, including local resource handling. The four baseline processes are expected runtime roles. Changing process flags to save memory would alter isolation or rendering behavior. [Electron process model](https://www.electronjs.org/docs/latest/tutorial/process-model) · [Electron security checklist](https://www.electronjs.org/docs/latest/tutorial/security) |
| Editor and language loading | The first tab imports a roughly 2.86 MB minified Monaco bundle. C/C++ and other registered tokenizers live in separate chunks. The configured worker URL is a separate asset. The code does not register TypeScript, JSON or HTML language-service clients. Monaco 0.57 stops its editor worker when the last model is removed. Its standalone services and low-frequency idle-worker timer live with the initialized renderer realm. The editor keeps up to three recent models with listeners and view state, and stores dirty text when a model is evicted. The 0.2.0 editor can park with no models while Workbench is open. Loading the editor leaves its module definitions in the renderer. |
| Renderer updates | The App coordinates settings, document subscriptions, output and panel state. The explorer reads directories as they expand. An expanded tree can render many rows, and changes to selected-path and parent callbacks can invalidate subtree memoization. Profile large expansions before adopting virtualization or deeper memoization. Ordinary typing uses Monaco instead of rebuilding React state for each character. |
| Files and persistence | Main applies path checks, atomic writes and file-revision checks. The file reader accepts UTF-8 source up to 2 MiB. The directory read limit is 4,000 entries. There is no file watcher, recursive search index, or database daemon. Preferences, learning history, project specs and practice metadata are local bounded JSON. User source and dirty drafts still consume memory, as expected for open work. |
| Learn, Projects and Practice | The renderer and main-service code are loaded separately on demand. Lesson files load one at a time. Project refresh is event-driven with debounce and cleanup. The baseline retained initialized service instances or their workspace reference after some close paths. Resource lifecycle changes should clear disposable service state and cancel work while retaining saved files and unsaved user drafts. |
| Compiler and tests | The C runner starts only on a request, using an installed compiler and temporary executable. Timeouts, output limits, process-group cancellation and cleanup protect ordinary use. Practice batches compile once and run inputs separately. A deliberately detached program can escape group termination. The runner is not an OS security sandbox. |
| Planning and networking | No application-level polling, telemetry, AI agent or autonomous network service was found. Online planning fetches only after explicit consent in Projects, uses a bounded request and encrypted credentials in main, and can be aborted. Renderer requests to external origins are blocked in production. |
| Dependencies and distribution | `npm ls --omit=dev --all` shows React, React DOM, Monaco and their transitive packages, with React deduplicated. No alternative runtime dependency was added. The installed 0.2.0 app is 267,208,225 logical bytes, while the app payload excluding Electron is about 3.72 MB. The largest packaging opportunity lies in choosing a different runtime, rather than shaving source modules. |

The shipped build is validated on Apple Silicon macOS. macOS Intel, Windows and Linux have no equivalent execution data. For a system-WebView candidate, Windows WebView2 and Linux WebKitGTK would require separate deployment, behavior and memory measurements. [Tauri WebView versions](https://v2.tauri.app/reference/webview-versions/)

## Alternatives and compatibility cost

## Prioritized optimization backlog

| Priority | Evidence and next step | Verification and trade-off |
| --- | --- | --- |
| 1 | Give activated optional features explicit owners and disposal. Close project subscriptions and queued tests, abort planning requests, and discard releasable history caches. Keep unsaved buffers and local files. | Repeated panel activation/deactivation with draft preservation, queued-work and process assertions, and long-idle samples. ESM remains cached by the renderer after its first import. |
| 2 | Release editor instances and workers when no editor surface needs them. Check last-window closure separately from process quit. Keep the editor mounted across profile switches to avoid disrupting in-progress work. | Check dirty files, undo where promised, and quick tab-switch latency. Measure last-window helpers and the cost of opening the editor again. |
| 3 | Keep compilation opt-in and separately measure toolchain activity. Approved automatic work must be bounded, debounced and tied to an active owner, with no background run in Minimal Mode. | Verify approval, stale-revision handling, cancellation and cleanup. Keep manual output and diagnostics unchanged. |
| 4 | Trace large explorer updates and editor input before restructuring React. Narrow subscriptions or virtualize only if measured interaction cost warrants it. | Hold folder structure, active selection, viewport, OS and input scenario constant. Validate navigation and accessibility. |
| 5 | Evaluate a product-equivalent system-WebView spike if the process floor still misses the targets. Benchmark with the same editor and the same security controls before testing a second editor. | Phase the bridge migration, preserve the current app and data format, and compare files, save conflicts, menus, IME, accessibility, compiler cancellation and offline packages. Validate on target macOS versions and separate Windows/Linux hosts before changing the default runtime. |

A migration plan starts with an isolated macOS candidate implementing the existing file, menu and run contracts. Measure it against the production baseline under the same workloads, using the same memory counter and a comparable release configuration. Continue only if the candidate shows repeatable target improvement and editor/backend parity. Evaluate CodeMirror behind an editor adapter in a separate experiment after the runtime result, so the two costs remain distinguishable. Retain the current installer and project storage as a rollback path until the candidate passes platform and security gates.

## Matched macOS host probe

The two web probes render the identical frozen 0.2.0 Ion React/Vite frontend, load its real Monaco C tokenizer, and open the same 650-line synthetic C buffer in a visible 1260 × 790 content area. The local HTTP fixture serves only on loopback. It substitutes a fixed bridge for Electron's real privileged backend and omits file writes, menus, project services and toolchain work. This isolates the frontend/runtime comparison. It does not reproduce an equivalent Tauri application or Ion's actual bundled local protocol. The AppKit probe uses the same window size and editable synthetic text with no syntax tokenizer, workbench, tabs or runner.

The Apple M3 machine had 24 GiB RAM and arm64 macOS 27.2 (26B123), on battery. Electron was 45.2.3. Three trials rotated host order. Each host started twice per trial, for 18 visible process launches, then the second launch collected 2.5-second samples after a 1.5-second Welcome settle and 1.2-second editor settle. Web readiness is launch to Welcome DOM plus two animation frames and a loopback message. Native readiness is launch to the text window's first display request and stdout marker. The C-open latency is from invoking the renderer's Open File button to recognizing the Monaco buffer plus two animation frames. AppKit starts with the file already open. The benchmark does not measure presented FPS or physical keyboard/IME latency.

| Metric | Electron + Monaco probe | WKWebView + Monaco probe | AppKit plain text probe |
| --- | ---: | ---: | ---: |
| First process of trial, median ms [range] | 349.39 [340.06–365.85] | 411.37 [405.34–877.09] | 205.85 [195.70–216.18] |
| Process relaunch, median ms [range] | 374.81 [368.55–384.81] | 379.00 [372.65–382.79] | 205.90 [202.20–215.36] |
| Welcome or initial text, summed RSS MiB | 399.34 | 179.33 | 97.39 |
| Welcome or initial text, attributed footprint MiB | 129.88 | 79.83 | 25.61 |
| Welcome or initial text, idle CPU % of one core | 0.10 | 0.48 | 0.04 |
| Open first C buffer, median ms [range] | 112.10 [104.20–118.80] | 175.00 [166.00–182.00] | Initial text is the startup marker |
| Settled with C buffer, summed RSS MiB | 467.98 | 323.64 | 97.39 |
| Settled with C buffer, attributed footprint MiB [range] | 203.97 [203.77–208.43] | 180.99 [177.28–235.61] | 25.61 [25.59–25.81] |
| Settled with C buffer, idle CPU % of one core | 0.07 | 0.88 | 0.04 |

All point values are medians of three samples. CPU is rounded to two decimals. The initial raw capture named its cumulative CPU counters as nanoseconds, but an independent spin calibration on this host showed they were Mach ticks. The table applies the measured 125/3 ns per tick. The original record is preserved and corrected CPU samples are in `performance-results/architecture-2026-11-09T05-07-29.469Z.cpu-calibration.json`. The shared sampler now normalizes time at collection. First and second launches leave OS caches untouched. Electron uses the same disposable profile for the second launch. The WebKit host uses a nonpersistent store, so second-launch app-cache reuse differs. Absolute startup timing is limited by those cache differences and by the distinct native readiness marker.

The Electron process family included its host and three helpers. The WebKit family included the host plus newly observed GPU, WebContent and Networking XPC peers. The native result was one host process. Attribution matches Electron's profile or descendants and newly created WebKit role names, with the probes launched serially. System services outside these groups are excluded. A process-family ledger sum is attributed footprint, not unique resident pages. The WKWebView editing footprint's high sample included a 67.84 MiB GPU ledger charge, versus about 13 MiB in the other two runs. No outliers were dropped. One short session per sample cannot establish sustained CPU or footprint behavior.

On this frontend, WKWebView's Welcome footprint median was 38.5% lower and its one-file median was 11.3% lower. The C buffer took 62.9 ms longer to open, a 56.1% increase. That is sufficient evidence to investigate a parity-tested system-WebView host, with editor responsiveness and GPU memory as explicit gates. It does not establish a migration benefit for the full IDE. The AppKit result establishes what this plain-text workload cost on this Mac. Existing syntax, tools, file safety and editor behavior would need separate implementation and measurements.

The measured renderer assets are 3,632,696 logical bytes. The bare Electron runtime application is 264,837,297 bytes and the Electron probe host script is 1,524 bytes. The combined Swift host executable is 91,224 bytes and relies on installed Apple frameworks. These are payload counts, not comparable installers. The native host also links WebKit in this probe, although it does not instantiate a web view in plain-text mode. Tauri/CodeMirror payload and real installer size are unmeasured.

Reproduce from this checkout with Xcode command-line tools, installed project dependencies and a production renderer directory. Run it away from other benchmarks and WebKit launches.

```sh
node scripts/architecture-probe.mjs \
  --renderer performance-results/phase2-resource-baseline/renderer \
  --trials 3 --idle-ms 2500
```

The probe adds no production dependencies, opens only disposable profiles, stops its test hosts and removes its temporary compilation and source fixture. The test scripts can be removed independently of the shipping app. Full raw measurements with individual process identities and ledger samples are in `performance-results/architecture-2026-11-09T05-07-29.469Z.json`. Windows, Linux, Tauri execution, CodeMirror behavior, presented frame rate and GPU utilization were not validated by these probes.

## 0.3 implementation status

- Resource profiles and explicit panel lifetimes are in the shipping build. Minimal exits after the last window and disposes an empty editor widget. Full preserves the optional warm widget and macOS Dock resume behavior.
- The panel component and desktop service activation now start together. Closing releases panel-owned snapshots, subscriptions and scheduled work. A renderer cannot unload imported ESM modules without resetting its realm.
- Automatic verification is Full-only and opt-in per approved test. The scheduler keeps a bounded queue and one debounce timer. The runner checks the source revision and content digest, compiles the validated saved bytes, and rechecks before execution.
- No production packages, OS services, watchers, or helper processes were added. The architecture probes are development tools.
- File authorization paths are held for the current window, including previously opened files across folder changes. They contain paths, not source contents, but the set has no numerical cap. A future path-lease change should track live tabs, outstanding reads and independently authorized files before evicting grants. Preserve the ability to save and switch back to open files.
- The next architecture experiment should reproduce real editor and runner behavior, including IME, menus, clipboard and scoped filesystem operations. A smaller prototype's idle result alone is insufficient to choose a shipping runtime.
